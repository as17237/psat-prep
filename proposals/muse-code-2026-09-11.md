# Proposal: Generic Exam Prep Framework

## 1. Findings from the existing codebase

What I actually read (no shell was available in this session — `bwrap` failed every
`bash` invocation — so counts below are read from code/comments, not re-executed;
I flag each as read-vs-measured): `README.md`, `package.json`, `api/package.json`,
`srs.js` (facade), `js/engine/grading.js`, `js/engine/scoring.js`,
`js/engine/adaptive_config.js`, `js/engine/storage.js`, `js/engine/examgen.js`,
`js/engine/sync.js`, `js/engine/attempt.js`, `js/shared/storage.js`,
`js/pages/student.js`, `api/src/lib/datamodel.js`, `index.html` (head),
`CLAUDE.md`.

### What already generalizes cleanly

- **Pure, dependency-free engine core.** `js/engine/` holds grading (SM-2 grades,
  free-response tolerant grading, scientific parser), scheduling, scoring,
  storage, exam generation, sync, exam state, and attempts as UMD modules with
  no DOM access. `srs.js` is now a compatibility facade recomposing the parts
  into the frozen `PSAT_ENGINE` object, with the API surface pinned by
  `tests/test_engine_api_surface.js`. This is the single best asset to carry
  forward: logic that runs identically under Node and the browser, unit-pinnable
  offline. Any framework keeps this shape — pure core, thin adapters.
- **Single source of record for tunables.** `js/engine/adaptive_config.js`
  (WI-16) lifts `SCALING_ASSUMPTIONS`, `OFFICIAL_BLUEPRINTS`, and `PSAT_89_SPECS`
  out of `scoring.js`, with explicit provenance comments separating published
  facts (120–720 section scale, 240–1440 total, blueprint domain targets) from
  hand-authored unvalidated estimates (power-curve exponents, `EASY_TRACK_MAX`,
  `ROUTING_THRESHOLD`). `scoring.js` re-exports them so the public API is
  byte-identical. That provenance-labeling discipline is exactly what a
  multi-exam framework needs per exam config.
- **Honest scoring gates.** `calculateScaledScore` and `scoreShortTest` enforce
  `MIN_PER_SECTION = 15` (and 30 total with both sections ready), return `null`
  with `reason` strings below the gate, use Wilson 90% intervals combined in
  quadrature, and label short-test results as single-test estimates excluded
  from full-mock trends. The project learned this the hard way (scores from
  8-question quizzes); the gate-plus-provenance pattern generalizes directly.
- **Data-loss paranoia that works.** Three mechanisms worth keeping: (a) the
  self-verifying slim codec in `api/src/lib/datamodel.js` — `slimProgressEntry`
  / `slimSrsCard` round-trip `JSON.stringify`-compare their own output and fall
  back to verbatim `$r` storage on any mismatch, so compression can only fail to
  save bytes, never corrupt; sharding (`pshard_`/`sshard_`, 16 FNV-1a buckets on
  the same partition key) addresses the measured 3.29 MB-at-full-coverage vs.
  Cosmos 2 MB-per-document limit; (b) `runTransactionalAction` +
  `createClientSnapshot` (5-snapshot ring) aborts or rolls back destructive
  actions when the pre-action snapshot fails; (c) delta sync (`buildSyncDelta`)
  with a documented convergence argument against `api/src/lib/merge.js`
  per-key merges plus a forced 24 h full push and cursor invalidation on every
  wholesale rewrite, so delta and full converge byte-identically.
- **Ephemeral attempt separated from lifetime record.** `js/engine/attempt.js`
  fixes the SRS-01/SRS-02 class (lifetime `answered` flag driving render logic,
  double-counted `timesSeen`) with an `OPEN`/`GRADED` attempt object carrying
  `FIRST_SEEN`/`SRS_REVIEW`/`PRACTICE` mode and a content-derived stable id
  shared with the outbox op for dedup. Clock-free and pure. A framework-level
  attempt event looks like this.
- **Twin-fix discipline.** `js/shared/storage.js` documents its dedup ledger
  (`safeGetStorage`/`safeSetStorage` 3 sites → 1, badge-callback injection via
  `onPendingSyncCountChanged`), and `js/engine/attempt.js` centralizes the ONE
  timing-reliability rule both practice and exam paths call. `CLAUDE.md`'s
  mode-2 rule (grep every site, fix all in one commit) is lived practice here.

### What will fight generalization

- **Single hardcoded student, no auth.** `getEnvironmentConfig` returns
  `default_student` (or `beta_default_student`); the sync endpoint and Cosmos
  partition key follow. Multi-student/multi-account is not a flag away — it
  needs identity, per-user lanes, and server-side authorization on every
  endpoint from day one.
- **PSAT-shaped constants threaded through logic.** Blueprint assembly in
  `examgen.js` (`_assembleModuleByBlueprint`, MCQ/SPR domain targets like
  Algebra 6/2, 27/27/22/22 modules, 98-question totals, `q.test === 'Reading and
  Writing' | 'Math'`) and scoring tracks (`Standard`/`Hard`/`Easy`/`Baseline`)
  assume this exam. `examgen -> scoring` has a clean one-way edge today, but a
  second exam type would touch both files without a config seam.
- **UX entangled with logic in places.** `renderRationale` in `grading.js`
  (engine!) emits Tailwind class strings and inline `onclick` handlers; page
  controllers (`js/pages/student.js`) hold grading-adjacent branching and the
  Web Component set under `js/components/` is page-serving, not themed. The
  `engine`/`pages`/`shared` split is real but porous — styling is not yet
  independently replaceable.
- **Legacy schema aliases as load-bearing code.** Real record shape is `type`
  (not `question_type`), `question_text` (not `prompt`), `options` as an array
  of `{key, text}` — yet `examgen.js`/`storage.js` still carry
  `(q.type || q.question_type)` and `(original.question_text || original.prompt)`
  fallbacks everywhere. A framework needs one versioned content schema with a
  migration, not perpetual OR-chains.
- **Proprietary backend shape.** Azure Functions v4 Consumption + Cosmos DB
  (`@azure/cosmos`, `@azure/storage-blob`) with hand-rolled merge semantics in
  two places (`js/engine/sync.js` client, `api/src/lib/merge.js` server) that
  must agree. Cheap at this scale, but partition-key-as-lane isolation,
  document-size sharding, and consumption-plan cold starts are incidental
  complexity a generic framework should not inherit by default.
- **Browser payload and key design are single-tenant.** The whole
  `data/questions_data.js` bundle parses eagerly; storage keys are bare
  `psat_*` with a `beta_` prefix hack for lanes; in-progress exams stay on the
  originating device while only completed reports upload. All three need
  rethinking per student, per exam, and per device.

## 2. Proposed framework model (multi-subject, multi-student)

### Core entities

- **Exam config (the framework's unit of reuse).** An admin/parent-authored,
  versioned document: sections → modules (counts, time limits, routing rules),
  domain/skill blueprints with target/min/max per module, item-type mix
  (MCQ vs. constructed response), scoring recipe (scale floors/ceilings, track
  curves with provenance flags, minimum-sample gates per section and per test),
  and adaptive rules (routing threshold, pool definitions). This is
  `OFFICIAL_BLUEPRINTS + SCALING_ASSUMPTIONS + PSAT_89_SPECS` promoted from a JS
  constant to validated data (JSON Schema, version string like
  `PSAT89_2026_V1` generalized to `<exam>_<edition>_V<n>`). `examgen` and
  `scoring` both consume it; neither owns it. Adding SAT, ACT, or a state test
  is a new config document plus content, not a code change.
- **Question bank against the config.** One versioned content schema
  (`id`, `exam`, `section`, `domain`, `skill`, `difficulty`, `itemType`,
  `stem`, `options[]`, `key` with multi-form support, `rationale`,
  `media[]`, `completeness` flags). Validate on import (the current
  `validator.py` + `import_validate.js` pair, but schema-driven per exam, not
  PSAT-hardcoded). The `text_complete: false → image-is-authority` pattern and
  the `extractAcceptedForms` multi-form grading (including the `either 8 or 9`
  prose case) become generic content-contract behaviors. Banks are addressed by
  `(exam, edition)` so two exams never share an id namespace.
- **Student + guardian accounts.** `student` (learner), `guardian` (parent),
  `admin` (config/content publisher). Every record carries `studentId`;
  guardians hold a membership edge to 1+ students. This replaces
  `default_student` and the `beta_` prefix hack. Device-local keys become
  namespaced (`<app>.<studentId>.<key>`), and the server authorizes every read
  and write by authenticated principal — the current endpoints' biggest gap.
- **Attempt as append-only event (the source of truth).** Keep `attempt.js`'s
  ephemeral attempt, but persist each closed attempt as an immutable event:
  `(attemptId, studentId, questionId, examId?, mode, response, correct,
  timeSpentMs, timingReliable, deviceId, clientVersion, schemaVersion, ts)`.
  Lifetime aggregates (`timesSeen`, SRS cards, session day rollups, score
  inputs) are *derived projections* rebuilt from the event log, exactly as
  `deriveSessionsFromProgress` already derives sessions from progress. History
  is never rewritten to fix the UI; corrections are new events. This is the
  current `buildProgressEntry` + `attempts[-3]` idea taken to its conclusion:
  keep the full log server-side, keep bounded projections client-side.
- **Derived state stays small.** Client keeps what it has today — lean
  projections (`toLeanReport` shape), SRS cards with capped history, per-day
  sessions — rehydrated against content on demand (`rehydrateReport` pattern).
  The server keeps the unbounded log. Quota pressure disappears by construction
  instead of by codec heroics.

### What changes vs. what survives

- Changes: identity/auth everywhere; exam config extracted from code to data;
  one content schema with migrations (retire the `||` alias chains after a
  one-time backfill); server-owned merge replaced by event append + projection
  rebuild; per-student namespaced storage; content served per exam/section, not
  one eager 6 MB bundle.
- Survives: the pure-engine discipline (grading, SM-2, Wilson-interval scoring
  with minimum-sample gates and estimate labeling), the self-verifying codec
  habit applied at projection boundaries, transactional snapshots for
  destructive device actions, delta sync semantics (now deltas of events, which
  are naturally idempotent by `attemptId`), and the attempt/mode separation.

## 3. Stack recommendation and rationale

Evaluated against the prompt's eight properties. My lean: **TypeScript with a
functional-style discipline, not a functional-first runtime.**

- **Strong typing.** TypeScript (strict) is the pragmatic pick. The current
  codebase's recurring defects are schema-shape bugs (`type` vs.
  `question_type`, array-vs-map options, single-vs-multi-form keys) — exactly
  what `Question`, `AttemptEvent`, `ExamConfig`, `Projection` interfaces plus
  JSON Schema validation at content import catch at build time. T frames every
  other property below; untyped JS at multi-exam scale re-pays this project's
  review history.
- **Functional style.** Keep the current ethic — pure functions, immutable
  data, explicit `now` parameters (already the pattern in `attempt.js` and
  `calculateStreak(map, todayKey)`), no module-closure mutable state — but
  enforce it by lint (`eslint-plugin-functional`, `readonly` types) and by
  keeping the engine importable without DOM. On ClojureScript: I judge it not
  worth it here. It wins on immutability-by-default and REPL-driven modeling,
  but it loses on the properties that matter more for this project: AI-agent
  familiarity (far fewer correct ClojureScript completions, weaker refactor
  tooling), hiring/replacement cost for a household-scale project, and
  interop friction with the Postgres/OTel/Playwright ecosystem. A
  functional-style discipline on TypeScript captures ~80% of the plug-in
  benefit (new exam = new pure module + config, no edits to existing modules)
  at ~10% of the friction. Genuinely uncertain — see §7.
- **Separation of concerns.** Enforce by repo structure (§4) plus a hard rule:
  the engine package may not import DOM, CSS, fetch, or storage APIs (today's
  `renderRationale`-emits-Tailwind violation becomes a compile error via
  package boundaries). Styling moves to a token/theme layer; persistence moves
  behind a repository interface the engine never sees.
- **Data sanctity: event-sourced, but narrowly.** Attempt events append-only is
  a good fit — the domain is already event-shaped (answers happen once, order
  matters, history must survive merges), and the current timestamp-winner
  merges in `sync.js`/`merge.js` are the complexity an event log dissolves:
  concurrent devices append different ids, union is the merge, projections
  rebuild deterministically. But I do NOT recommend full CQRS/event-sourcing
  framework ceremony (streams, sagas, snapshots-as-events). Keep one `attempts`
  table plus materialized projection tables rebuilt by a single versioned
  reducer — the `datamodel.js` purity rule (pure, unit-pinnable against real
  data) applied to the reducer. Conventional mutable rows for accounts,
  configs, and content; append-only only for learner evidence.
- **Ease for AI coding agents.** Small pure functions with explicit interfaces
  and hand-written contract tests are the most agent-legible shape in this
  repo's history (the engine parts are; the 2,700-line inline page scripts
  were not, hence WI-09). TypeScript helps agents more than it helps humans
  here: the compiler rejects the imagined-schema bug before review. Keep files
  small, forbid ambient globals (`window.PSAT_CLIENT_VERSION` style), pass
  context as arguments.
- **TDD.** Core logic stays runtime-free (Node `vitest`, no browser) — the
  current offline suites already run this way. UI gets component tests plus the
  existing Playwright harness (which already uses synthetic profiles and an
  intercepted sync API — keep that pattern, extend to multi-student fixtures).
  Require the repo's standing rule for new generation/filtering logic: a test
  against the real bundle asserting real counts, with expectations written by
  hand and the test seen red before green.
- **Fast deployment feedback.** A Vite-built static frontend (still servable
  from any static host during dev via preview) + containerized API behind
  Compose locally and a small managed container host in prod. The current
  zero-build setup optimizes first-paint simplicity but punts typechecking,
  bundling, and cache-busting onto conventions; at multi-exam scale the
  30-second `typecheck + unit + preview` loop pays back. Keep `python3 -m
  http.server`-equivalent one-command local run as a documented requirement.
- **Performance (tie-breaker).** Code-split per exam/section (fixes the eager
  6 MB parse), lazy-load charts/calculators (already started with Chart.js),
  serve images as sized, cached objects — not 325 MB of PNGs alongside the
  bundle. Either stack choice is fast enough; this breaks ties toward Vite +
  static CDN, not toward server rendering.

## 4. Architecture and module boundaries

One repo, hard package boundaries (enforced by `eslint-plugin-import` /
`tsconfig` project references so a wrong-direction import fails CI, not
review):

- `packages/core/` — pure engine (grading, scheduling/SM-2, scoring, exam
  assembly, projections reducer, attempt lifecycle). No DOM, no I/O, no clock
  reads (time passed in). Versioned, published API manifest like today's
  `API_MANIFEST` + surface test. New exam support = new `ExamConfig` document
  + optional pure strategy module implementing a `ScoringRecipe` /
  `RoutingRule` interface — never an edit to an existing exam's module.
- `packages/content/` — schema, validators, import pipeline (Python or TS
  port of `extractor → validator → extract_questions → rebuild_bundle`),
  per-exam bundles + media manifest. Content builds are hashed artifacts;
  the client fetches `(exam, edition, section)` slices, never the whole bank.
- `packages/api/` — HTTP API over the event log + projections (attempts
  append, projections read, configs/content read, guardian membership
  checks). Stateless containers; merge logic shrinks to idempotent insert +
  projection rebuild — the current dual `sync.js`/`merge.js` winner-picking
  goes away.
- `packages/web/` — student, guardian, and admin apps sharing a component +
  theme layer (`tokens.css` grown into real design tokens; components take
  data props, never import engine internals). Page controllers stay thin:
  render projections, emit attempt events.
- `packages/ai/` — the insights seam (§6); depends only on `core` types and
  read models, never on web components.
- `infra/` — Terraform + Compose + migration scripts; backup/restore drills
  as runnable scripts (today's `preflight_backup.sh` /
  `weekly_restore_check.sh` pattern, generalized per environment).

How this prevents "hard refactor per feature": the only cross-exam code is
`core` interfaces and the config schema. A SAT module cannot break PSAT
because it cannot import PSAT's module — it implements the same interface
against a different config. The repo's mode-2 failure (same rule fixed in N
places) becomes structurally impossible for exam-specific rules: the shared
rule lives in `core` once, the exam-specific rule lives in exactly one
strategy module.

## 5. Cloud, deployment, and environment rotation (pre/prod/old)

**Primary: a portable Postgres + containers stack.** Postgres (managed, e.g.
Neon/RDS/Cloud SQL — pick one, Terraform abstracts it) for accounts, configs,
content refs, attempt events, and projection tables; object storage for
question media and backup archives; one container image for the API and one
static build for the web, deployed via Terraform to any container host
(Fly.io/Cloud Run/App Service — the choice is deliberately boring). No
Cosmos-proprietary features, no Functions-proprietary triggers in the hot
path. Exception I would allow: keep a serverless-function front for the
attempts-ingest endpoint only if idle cost dominates — but behind the same
container image via an adapter, never as a second codebase.

**Rough cost at low usage** (single-digit households, hundreds of attempts per
month): ~$10–25/mo total — smallest managed Postgres (~$5–10), object storage
cents, container host scale-to-zero or single shared instance (~$5–10),
backups cents. The current Consumption + serverless-Cosmos shape is cheaper at
zero and spikier under load; Postgres wins on tool familiarity, transaction
semantics for the event append, and freedom to leave the provider.

**pre → prod → old rotation with data intact:**

- **Environments are app deployments, not data silos.** One Postgres cluster;
  `pre`, `prod`, `old` are three connection/config targets against versioned
  schemas, with exactly ONE writable learner-data lineage at a time
  (`prod`). Promotion `pre → prod` retires current `prod` binaries/config to
  `old` (rollback = repoint traffic + rerun the idempotent projection
  rebuild), but learner events are never copied, forked, or "rotated" — they
  live in tables outside the deployment swap. Rollback therefore cannot strand
  attempts: events appended while the new `prod` served are still there when
  `old` resumes serving, and projections rebuild deterministically from them.
  Schema migrations are expand-then-contract (additive in `pre`, backfilled,
  old code tolerates new columns) so both `prod` and `old` binaries read the
  same tables during the window.
- **`pre` test data.** Nightly anonymized seed: production *shapes* (real exam
  configs, real content build, distribution-matched synthetic attempts for a
  handful of fixture students) — never real learner rows. Synthetic fixtures
  are marked (`isSample`, separate `studentId` namespace) per the repo's
  demo-mode lesson, with a banner wherever they render. `pre` may read prod
  content artifacts by hash but never prod learner tables (separate DB role).
- **Backups and verified restore.** Continuous WAL/archiving + nightly
  `pg_dump` to object storage with content-hash manifests; retention policy
  unit-tested with generative tests over decorrelated timestamps (the repo's
  WI-22 lesson: hand-built fixtures passed while fuzz at seed 11 caught the
  real defect — require the fuzz). Keep the current gates generalized:
  pre-promotion backup attestation (`PREFLIGHT_BACKUP_OK <file>`) and a weekly
  restore-to-scratch drill that only counts with its red demonstration
  (`WEEKLY_RESTORE_CHECK_OK <folder>`), run at every phase boundary.

## 6. AI insights integration

One seam, three rules: the model is swappable, prompts are versioned data, and
the AI package never writes learner state directly.

- **Where it lives:** `packages/ai/` exposes `explain(question, attemptContext,
  readingLevel)`, `narrateTrend(projectionSlice)`, and
  `suggestFocus(projectionSlice, examConfig)` — pure against `core` types plus
  a `ModelAdapter` interface (`generate(prompt, jsonSchema) → validated
  object`). Providers (Anthropic/OpenAI/Gemini/local) implement the adapter;
  swapping one is a one-file change with contract tests asserting schema-shaped
  output, timeouts, and refusal handling.
- **Prompts and explainers as content.** The current `explainers/` +
  `explanations/` HTML artifacts and the explainer skill become versioned
  templates with reading-level parameters, rendered through the same theme
  layer as the app and cached by `(questionId, templateVersion, level)` —
  never inline model prose stored as fact. Parent-facing narratives carry the
  same provenance labeling as scores: measured numbers in, hedged language
  out, `Reliable: false` when the sample gate fails.
- **Write path.** AI output lands as *suggestion* records (focus areas, draft
  explanations pending review), never as direct writes to attempts or
  projections. Human/reviewer approval promotes a suggestion to content. All
  calls logged with `(modelId, promptVersion, inputHash)` for audit and
  cost tracking.

## 7. Trade-offs and where other models may disagree

1. **TypeScript-discipline vs. ClojureScript (or ReScript/Gleam).** I pick TS
   for agent familiarity and ecosystem over language-enforced purity. Others
   may reasonably pick ClojureScript for true immutability and data-driven
   exam configs as EDN. I lean TS because this project's defects were
   schema-shape bugs a typechecker catches, not state-modeling bugs needing a
   new runtime — but I am the least certain here.
2. **Narrow event log vs. conventional mutable CRUD.** I keep append-only for
   attempts and mutable rows elsewhere. Others may argue for full event
   sourcing or, oppositely, for staying with timestamp-winner merges extended
   per student. Full ES adds operational ceremony this scale does not need;
   extended winner-merges re-inherit the dual-implementation drift (`sync.js`
   vs. `merge.js`) the log dissolves. The middle path is deliberate.
3. **Postgres vs. staying on Cosmos/serverless.** I trade the current
   near-zero idle cost and partition-key lanes for transactions, ad-hoc
   analytics (`GROUP BY skill` without shard fan-out), and portability. A
   cost-first reviewer may keep Cosmos + Functions and add auth/sharding only.
   At hundreds of attempts/month both work; I weight operability over idle
   dollars.
4. **Vite + build step vs. preserving zero-build.** I accept a build for
   typecheck/code-split/cache-busting. Others may keep the no-build UMD/ES
   split that served offline testing well. I think multi-exam code-splitting
   tips it — shipping every exam's bank to every student does not survive
   generalization.
5. **Monorepo + package-boundary lint vs. separate repos/services.** I keep
   one repo with compile-enforced boundaries so an agent cannot accidentally
   entangle engine and UI. Others may split `core` into its own versioned
   package or services per bounded context. Separate repos add release
   coordination this team (AI agents + one human) will feel more than the
   coupling they prevent.

## 8. Open questions for the human reviewer

- Which exams are actually next (SAT, ACT, state tests)? The config schema's
  required flexibility (adaptive MST vs. linear vs. per-section timing, SPR vs.
  all-MCQ) depends on the second exam, not the first.
- Is offline-first (device-originated in-progress exams, outbox sync) a
  must-keep, or may `prod` assume connectivity with offline as
  best-effort? It drives the outbox/projection-cache design.
- Real-student PII posture: COPPA/FERPA expectations for multi-student
  accounts, data-retention window for attempt events, and whether parent
  accounts may export/delete a child's log?
- Score-modeling ambition: stay with the current disclosed-estimate approach
  (linear map + Wilson intervals + gates) per exam, or invest in calibrated
  equating studies? This decides whether scoring stays in `core` or needs a
  psychometrics-owned module.
- What I could not verify (no shell in this session): bundle byte sizes,
  question-bank counts, and suite totals cited from code/comments above. Worth
  one `node -e` + `npm test` pass before merging this report's claims.
