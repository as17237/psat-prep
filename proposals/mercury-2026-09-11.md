# Proposal: Generic Exam Prep Framework

## 1. Findings from the existing codebase

**Architecture & Strengths:**

- **Modular engine design**: The codebase is split into well-separated UMD modules (`grading.js`, `scheduler.js`, `scoring.js`, `storage.js`, `examgen.js`, `sync.js`), each with clear responsibilities and dependencies. This is already close to a plugin architecture.

- **Pure function patterns**: Core logic (grading, scheduling, scoring, merge) uses pure functions with no side effects. The `api/src/lib/merge.js` module is a good example—completely testable without network or database dependencies.

- **Delta sync with cursor**: Implements a lightweight delta-sync mechanism that only sends changed records since the last push, reducing bandwidth.

- **Data sharding & compression**: Uses 16-bucket sharding for Cosmos DB with key shortening and derived-field elimination to compress data (~40% reduction achieved, aiming to avoid hitting the 2MB document limit).

- **Versioned migrations**: Implements v1→v2 migration with backup/rollback capabilities (`migrateLocalStateToV2`, `rollbackLocalStateToV1`).

**Patterns that will fight generalization:**

- **Hardcoded student identity**: `default_student` is derived from URL path. Multi-student support would require fundamental changes to authentication and data routing.

- **Tight coupling between exam generation and question bank**: The `examgen.js` module assumes PSAT 8/9 structure specifically. Exam configs are not externalized—changing sections, timing, or scoring rules requires code changes.

- **Schema coupling**: Storage keys (`psat_progress`, `psat_srs`, `psat_sessions`, `psat_exam_history`) are hardcoded. Adding new data types would require parallel refactoring.

- **Azure-specific infrastructure**: Azure Functions + Cosmos DB + Blob Storage are tightly coupled throughout the codebase.

- **No API schema**: The sync endpoint expects specific field names (`student_name`, `progress`, `srsState`, etc.). No OpenAPI/JSON Schema validation exists.

## 2. Proposed framework model (multi-subject, multi-student)

**Core abstraction layers:**

1. **Exam Config Schema**: Externalized configuration defining:
   - Sections (name, timing, question pool references)
   - Scoring rules (raw-to-scale conversion, section weighting)
   - Adaptive rules (routing thresholds, module selection logic)
   - Question bank associations

2. **User & Account System**: 
   - Parent/teacher accounts with student roster management
   - Role-based access control (RBAC)
   - Per-student data isolation with audit trails

3. **Question Bank Model**:
   - Subject-agnostic question structure with metadata (domain, skill, difficulty, tags)
   - Content versioning and review workflows

4. **Student Progress Model**:
   - Multi-subject progress tracking
   - Unified SRS scheduler across subjects
   - Cross-subject skill analytics

**What already generalizes cleanly:**

- The SM-2 scheduling algorithm in `scheduler.js` is already subject-agnostic
- The `storage.js` transactional patterns are reusable
- The merge/sync logic in `api/src/lib/merge.js` can be adapted for any record type

## 3. Stack recommendation and rationale

**TypeScript + Node.js (runtime):**

- **Strong typing**: TypeScript provides compile-time safety for an expanding codebase. The functional programming patterns can be enforced through code conventions rather than language choice.

- **AI-agent friendliness**: TypeScript's explicit interfaces, type annotations, and ubiquitous IDE support make it easier for AI agents to navigate and modify code correctly without deep context.

- **Ecosystem maturity**: Mature testing frameworks (Jest, Vitest), type validators (Zod), and build tooling (esbuild, Vite).

**Functional programming discipline (not a separate language):**

- **Why not ClojureScript**: Adds friction for AI agents and hiring. TypeScript with immutable data patterns (spread operators, `Object.freeze`, persistent data structures via libraries like Immutable.js) provides 80% of the benefit.

- **Implementation**: 
  - Pure functions for all core logic
  - Immutable state updates in UI layer (using Zustand or Jotai)
  - No shared mutable state; all mutations flow through explicit reducers/actions

**Frontend: SvelteKit**

- **Separation of concerns**: Component logic, styling, and state are naturally separated. Theme system is built-in.
- **Performance**: Compiles to vanilla JS; minimal runtime overhead.
- **AI-friendliness**: Simple, declarative syntax; easier to generate correct UI code than complex React patterns.

**Data layer: PostgreSQL (with JSONB)**

- **Why not Cosmos DB**: Postgres provides ACID transactions, better cost predictability, and portable SQL. JSONB supports the flexible document structure needed for progress tracking.
- **Append-only design**: Event sourcing for audit trails; student attempt history stored as append-only events with immutable IDs.

│   │   ├── parent/

├── insights/

**Plugin mechanism:**

- Scoring rules: Interface-based plugins registered at startup
- Exam types: Config-driven via `exam-config.ts`
- UI views: Component registration with capability flags

This structure ensures that adding a new exam type or scoring rule is a "plug-in module" operation, not a refactor of existing code.

## 5. Cloud, deployment, and environment rotation (pre/prod/old)

**Cloud: AWS (portable, standard components)**

- **ECS/Fargate**: Containerized backend (not vendor-locked serverless)
- **RDS PostgreSQL**: Managed Postgres with read replicas
- **S3**: Static assets and backups
- **CloudFront**: CDN
- **Estimated monthly cost at low usage**: ~$150-250/mo
  - RDS (t3.micro): ~$25/mo
  - ECS (minimal): ~$50/mo
  - S3/CloudFront: ~$20/mo
  - Monitoring/backups: ~$50/mo

**Environment rotation with data integrity:**

1. **Data isolation**: `student_id` is the partition key in PostgreSQL. All three environments (pre, prod, old) connect to the same database but filter by environment tag or use separate databases with replication.

2. **Rotation workflow**:
   - `pre` environment has staging data (copied from prod, anonymized)
   - Deploy to `pre` → run integration tests
   - Promote `pre` → `prod`: Switch load balancer
   - Current `prod` → `old`: Keep active for rollback (24-48 hour retention)
   - Database: All environments share same database; environment is tracked in request context

3. **Rollback**: 
   - Revert load balancer to point to `old` container
   - No data loss: student records are in shared DB, not containers
   - Verify data consistency before removing `old`

4. **Backups**: 
   - Automated daily Postgres snapshots
   - Point-in-time recovery enabled (7-day retention)
   - Backup verification tests run weekly

## 6. AI insights integration

**Seam design:**

```typescript
// insights/ai-service.ts
interface AIProvider {
  generateExplanation(questionId: string, studentAnswer?: string): Promise<string>;
  generateTrendNarrative(studentId: string, window: DateRange): Promise<TrendReport>;
  generateFocusAreas(studentId: string): Promise<FocusArea[]>;
}

class AIService {
  private provider: AIProvider;
  
  constructor(config: AIConfig) {
    this.provider = this.createProvider(config.provider);
  }
  
  private createProvider(type: string): AIProvider {
    switch (type) {
      case 'openai': return new OpenAIProvider(config);
      case 'anthropic': return new AnthropicProvider(config);
      case 'local': return new LocalProvider(config);
      default: throw new Error('Unknown provider');
    }
  }
}
```

**Location in architecture**: The `insights/` module sits alongside `engine/` and is called from:
- Question rendering (explainations)
- Parent dashboard (trend narratives)
- Drill generation (focus areas)

**Contract**: Provider-agnostic interfaces; configuration-driven provider selection; caching layer for cost control.

## 7. Trade-offs and where other models may disagree

1. **TypeScript vs. Rust/Go for core logic**: I chose TypeScript for AI-agent friendliness. Others might prefer Rust for performance/safety, accepting higher friction for AI codegen.

2. **PostgreSQL vs. event sourcing**: I recommend standard Postgres with JSONB for simplicity. Others might argue for full event-sourcing (Kafka + DB) to guarantee immutability of attempt data.

3. **Svelte vs. React**: I chose Svelte for simplicity and performance. Others might argue React has better ecosystem support for complex dashboards and more mature AI-codegen training data.

4. **AWS vs. GCP/Azure**: AWS is the "safe" choice. Others might argue for GCP (better ML integration) or Azure (enterprise alignment, existing presence in education sector).

5. **Multi-tenant database vs. database-per-tenant**: I chose shared database with row-level security for cost efficiency. Others might argue for isolation (database-per-tenant or schema-per-tenant) for security/compliance reasons.

## 8. Open questions for the human reviewer

1. **Compliance requirements**: What student data regulations apply (COPPA, FERPA, GDPR)? This affects data retention, consent flows, and possibly architecture (data residency, encryption).

2. **Scalability targets**: What are the expected user counts? The current architecture assumes hundreds to low thousands. For tens of thousands, we'd need caching layers, CDN for question assets, and possibly read replicas from day one.

3. **AI budget and latency tolerance**: What are acceptable costs per explanation? Should explanations be cached? Should we have fallbacks when AI is unavailable?

4. **Mobile requirements**: Is mobile web sufficient, or do we need native apps? This would affect whether we build a separate mobile stack or rely on responsive web.

5. **Question content licensing**: How will questions be sourced? If from third-party providers, we need API contracts and content ingestion pipelines.

6. **Parent/teacher UI requirements**: Are parents just observers, or do they need to intervene (assign drills, adjust settings)? This affects the complexity of the parent dashboard.
