# Proposal: Generic Exam Prep Framework

## 1. Findings from the existing codebase

This repo is a working, battle-hardened **single-exam, single-student** product, not a prototype. The product lessons are more valuable than the current stack. A from-scratch framework should keep those lessons as invariants and throw away the things that make them hard to keep.

### What it is today

- **Client:** four HTML shells (`index.html` 1,630 lines, `parent.html` 1,222, plus `mistakes.html` / `feedback.html`) with page controllers as native ES modules. `js/pages/student.js` is still 3,039 lines; `parent.js` is 1,362. No bundler; the app itself has no runtime dependencies (`package.json` exists only to pin Playwright).
- **Engine:** the old 3,400-line `srs.js` monolith was split (WI-10) into UMD parts under `js/engine/` — `grading.js`, `scheduler.js`, `scoring.js`, `examgen.js`, `storage.js`, `sync.js`, plus later `attempt.js`, `exam_state.js`, `test_planner.js`, `adaptive_config.js`, `persistence.js`, `gap_summary.js`. `srs.js` is now a 220-line facade that recomposes `PSAT_ENGINE`.
- **State:** `localStorage` keys `psat_progress`, `psat_srs`, `psat_sessions`, `psat_exam_history`, `psat_active_exam_state`, plus a recovery journal (`psat_pending_write`) and a sync outbox. Cloud identity is derived from the URL path in `js/engine/storage.js` → `getEnvironmentConfig`: production is hardcoded `default_student`; `/beta/` becomes `beta_default_student`; `/v2/` is **not** isolated and writes the live student.
- **API:** Azure Functions on a Y1 Consumption plan (`api/src/functions/{sync,backup,backupStatus,backupPrune,feedback}.js`). Every endpoint is `authLevel: 'anonymous'`. Student name is `request.query.get('student_name') || 'default_student'`. Sync target is hardcoded in the client as `https://psat-api-4915.azurewebsites.net/api/sync`.
- **Data:** a frozen 3,059-question PSAT 8/9 bank (`data/ela_questions.json` + `data/math_questions.json` bundled as `data/questions_data.js`, ~6.1 MB) plus 3,059 PNG question cards. Cosmos container `Questions` is a write-only mirror the running app does not read. Live student state lives in `UATStudentAnswers`, partitioned by `/student_name`, sharded 16 ways after a measured 2 MB Cosmos item-limit scare.

### Patterns that already work (keep as design law)

1. **Pure, clock-free engine functions.** `attempt.js`, `exam_state.js`, `test_planner.js`, `api/src/lib/merge.js`, `datamodel.js`, and `shardsync.js` take `now` / inputs as arguments, do not mutate them, and are unit-pinnable in Node with no DOM. This is the only reason six review rounds of defects eventually became testable.
2. **One rule, one module.** `adaptive_config.js` is the documented single source for blueprints and scaling constants. `test_planner.js` exists specifically because preview (`updateGapTestCalculations`) and launch (`generateCustomTest`) used to disagree. `questionImageSrc` collapsed four slightly different URL expressions. Twin-page drift is named as CLAUDE.md failure mode 2 and is still the main UX risk.
3. **Honesty about numbers.** `SCALING_ASSUMPTIONS` in `adaptive_config.js` separates published facts (120–720 / 240–1440 floors) from hand-authored estimates (`HARD_TRACK_EXPONENT`, `ROUTING_THRESHOLD: 0.58`, labelled `(unvalidated)`). `MIN_PER_SECTION = 15` and `MIN_SCORED_TEST_QUESTIONS = 30` refuse to show a scaled score on a biased or tiny sample. `test_planner.js` stamps every time estimate with `measured: boolean` and `basis`. A generic framework that lets a plugin print “Official SAT score” from 8 algebra items will recreate the worst bugs in this repo.
4. **Destructive actions are transactional.** `runTransactionalAction` snapshots first and aborts if the snapshot fails. Imports are validate → preview → explicit Merge / Replace / Cancel (`import_validate.js`). `exam_state.js` rule 1: *nothing here deletes anything*; expiry locks a module rather than calling `clearActiveExamState()`. Persistence is a write-ahead journal (`persistence.js`) that replays the same bytes, never re-grades.
5. **Merge is monotonic, not last-write-wins.** `api/src/lib/merge.js` (and the client twin in `js/engine/sync.js`) takes per-field maxima on counters, unions attempt tails and error tags, and will not let an incoming zero-answer day erase a stored day (DATA-02). This is what made a dual-frontend / single-data soak lane survivable. It is also explicitly **not** exact concurrent accounting (DATA-01: two devices off a shared base of 1 still merge to 2, because `max(2,2) = 2` without stable attempt IDs).
6. **Lean payloads.** Exam snapshots store question IDs only (`exam_state.js` rule 4; tests assert a 98-question snapshot stays under 20 KB). The repo has already shipped 193 KB and 209 KB `localStorage` records. Any new design that rehydrates full question objects into history will hit quota again.
7. **Real-data tests as the prime rule.** CLAUDE.md: execute the changed path against `data/questions_data.js` and paste the numbers. Integrity suites pin merge and the slim codec against a captured production document. Playwright E2E is quarantined onto synthetic students. This culture is the product.

### Patterns that will fight generalization

1. **Exam knowledge is not data — it is code.** `OFFICIAL_BLUEPRINTS` / `PSAT_89_SPECS` encode 27/27 RW and 22/22 Math, domain targets, SPR mix, and a 10-minute break. `scoring.js` branches on `'Reading and Writing'` vs `'Math'`. `examgen.js` hardcodes `HIGH_YIELD_DOMAINS` (`Algebra`, `Advanced Math`, `Information and Ideas`, `Craft and Structure`). Adding SAT, ACT, AMC, or a parent-authored spelling test means editing scoring, generation, UI copy, and parent analytics in parallel.
2. **Identity is a URL accident.** One student, derived from path prefix, with no authentication. `/v2/` writing `default_student` is a live isolation failure (`docs/RELEASE_RING_DESIGN.md` §3.3). Multi-student cannot be bolted onto `?student_name=`.
3. **The question record is almost generic, but the delivery is not.** The schema (`id`, `assessment`, `test`, `domain`, `skill`, `difficulty`, `type: multiple_choice | free_response`, `options[]`, `correct_answer`, `rationale`, `question_image`) would serve other banks. What will not: shipping the entire bank as a 6 MB JS assignment, treating PNG cards as the authority because 901 records are text-incomplete and ~900 have placeholder option text, and rewriting image URLs at deploy time with `sed` (`js/shared/questions.js` comment for `deploy_v2.sh`).
4. **UMD script-order coupling.** Engine parts throw if a predecessor is missing (`__PSAT_ENGINE_PARTS`). Pages mix classic `<script>` engine tags with ES module controllers that assume `PSAT_ENGINE` is already a global (`js/shared/env.js`, `js/shared/storage.js`). An incomplete deploy file list ships an app whose engine never initialises (happened in WI-22). This is the opposite of “add a plug-in module.”
5. **Storage and product names are PSAT-shaped.** `psat_*` keys, `PSAT_ENGINE`, `psat-prep-db`, `UATStudentAnswers`, `PARENT_API_BASE` baked into `parent.js`. Beta isolation is a string prefix (`beta_`), not an account.
6. **Cosmos shaped the data model around a 2 MB item limit.** WI-11.5 (`datamodel.js`) invented FNV-1a sharding, a self-verifying slim codec, and dual-write then shard-authoritative modes *because* one master document was projected at 3.29 MB at full-bank coverage. That complexity is a database limitation, not a domain requirement. A relational or event-log store would not need 16 progress shards and a frozen fallback map that `build_worklist.py` already misread once.
7. **UX and domain logic are still entangled in page controllers.** Math tools (Desmos + scientific calculator + reference sheet) are imported into both student and parent pages. Gap cards, Chart.js lazy-load, explainer index fetches, backup-status widgets, and exam-runner DOM live in the same 3,000-line controller. `styles/tokens.css` + `js/components/*` are the start of a theme layer; they are not yet a replaceable skin.
8. **AI content is static HTML, not a seam.** Cluster explainers (`explanations/SYSTEM.md`) are hand-built pages registered in `index.json`. There is no provider interface, no model/prompt hash, and no way to swap Anthropic for a local model without editing pages.
9. **Serverless Consumption cannot do the environment ring the product now wants.** `docs/RELEASE_RING_DESIGN.md` measured that Y1 has no deployment slots, so one Function App serves every lane. Lane isolation is therefore a client convention — and it is incomplete.

### The open wound the redesign must close

Milestone 3 is still open: there is no durable append-only attempt ledger with stable IDs. Counters are monotonic maxima over a 3-attempt tail (`ATTEMPT_LOG_CAP = 3`) and a 20-event SRS tail. `attempt.js` already emits versioned attempt events (`ATTEMPT_SCHEMA_VERSION = 1`) and says “Milestone 3 will ingest these.” A greenfield design should start there, not retrofit it onto a mutable progress map.

## 2. Proposed framework model (multi-subject, multi-student)

The unit of reuse is an **Exam Program**, not an app clone. One running system hosts many programs, many households, many students.

### Core nouns

| Noun | Meaning |
| :--- | :--- |
| **Account / Household** | Billing and data boundary. Parents and students belong here. |
| **Principal** | A person with a role: `owner`, `parent`, `student`, `teacher` (optional). Authn is on the principal; authz is on the household. |
| **Exam program** | A versioned config: sections, modules, timing, breaks, calculator policy, scoring model, adaptive routing rules, honesty gates (minimum sample, what may be labelled an estimate). |
| **Question bank** | Versioned items tagged with `programId`, section, domain, skill, difficulty, item type, assets. Assets (PNG/SVG/audio) are first-class, not a deploy-time path rewrite. |
| **Attempt event** | The source of truth. One stable-id event per submitted answer (and per skip, pause, expiry, import, reset). Append-only. |
| **Session / Exam sitting** | A lifecycle object (the current `exam_state.js` rules), referencing item IDs, deadlines, route taken. Never deleted on expiry. |
| **Derived views** | Progress, SRS cards, daily sessions, gap summaries, score estimates. Always recomputable from events. Cached, never canonical. |
| **Insight artifact** | Model-generated explanation or parent narrative, keyed by `(subjectId, promptHash, modelId, contentHash)`. Never written into the attempt log. |

An admin/parent creating “AP Human Geography 2027” or “custom grade-7 fractions” supplies an exam-program JSON and a bank. They do not get a fork of `scoring.js`.

### What changes vs today

- **Identity:** replace `default_student` / URL-path student names with signed-in principals. The API never accepts a client-supplied `student_name` as authority. Household-scoped student switcher for parents.
- **Config vs code:** lift `OFFICIAL_BLUEPRINTS`, `PSAT_89_SPECS`, `SCALING_ASSUMPTIONS`, `HIGH_YIELD_DOMAINS`, section names, and score gates into a versioned `ExamProgram` document. `PSAT 8/9 2026` becomes the first plugin, with its unvalidated curve flags preserved so the UI cannot call them Official.
- **Item types as plugins:** `multiple_choice` and `free_response` (numeric, with `extractAcceptedForms` / `gradeFreeResponse`) stay. Add a registry: `mcq`, `numeric`, `multi-select`, `constructed-response-rubric` (human or AI-assisted, never silently auto-scored as exact). Grading is `GradeFn(item, response) -> Grade`; the PSAT SPR parser is one implementation.
- **Generation as a planner over config:** keep the `test_planner.js` contract (preview ≡ launch, no silent filter relaxation, injected RNG, labelled assumptions) and drive it from the program blueprint rather than from `examgen.js` constants.
- **SRS as a scheduler plugin:** SM-2 in `scheduler.js` is already exam-agnostic. Keep it. Do not bury it in page controllers. Allow a program to disable SRS (a one-shot diagnostic) without code changes.
- **Analytics:** `gap_summary.js` already keys off `q.test` + `q.domain` + `q.skill`. That generalizes if those fields are program-defined dimensions, not PSAT vocabulary. Score projection must be a program-provided `ScoreModel` with the same honesty gate pattern (`minN`, `coverage`, `estimateBand`).
- **Client bank loading:** stop shipping 6 MB + 324 MB of images to every origin. Programs declare which items a sitting needs; the client fetches those items and assets (the offline-prep path in `docs/OFFLINE_MODE.md` already does this for one exam — ~120–150 images, ~15 MB). The full bank is a server/content concern.
- **Multi-student:** every event, sitting, and derived view is `(householdId, studentId, programId)`. Parent dashboard is a query over children, not a second copy of student metrics with slightly different thresholds.

### What already generalizes cleanly

- Attempt vs lifetime progress (`attempt.js` modes `FIRST_SEEN | SRS_REVIEW | PRACTICE`).
- Exam lifecycle (`exam_state.js`: lock on expiry, one remaining-time function, lean ID-only snapshots).
- Outbox + pull/push with readonly validation mode.
- Import envelope with Merge/Replace/Cancel and pre-action snapshots.
- Design tokens (`styles/tokens.css`) as a theme layer, with portal accent as a data attribute.
- The CLAUDE.md failure-mode list, promoted to framework lint/test rules.

PSAT 8/9 remains a first-class program pack: bank, images, blueprints, SM-2 defaults, parent builder, explainer templates. It is content + config, not the kernel.

### Feature map: what this becomes for the student and for the parent

Student and parent dashboards are two surfaces over the same fact set, not two implementations. Every metric shown to a parent is either the same measurement, or a labeled aggregate, of what the student sees. The features below split into **(✓ today)** — already present and worth carrying into the framework — and **(✚ framework)** — new or newly general capabilities the multi-subject, multi-student design makes possible.

**Student perspective**

| Area | Capability | Carry over? |
| :--- | :--- | :--- |
| Practice | Focused drills selectable by exam, section, domain, skill, question count, available minutes, and format/difficulty preference | ✓ (today's focused builder) |
| Immediate feedback | Per-answer grading, correct key, rationale, and a student-chosen error tag (concept gap, misread, vocabulary, strategy, calculation, graph/table, time pressure) | ✓ |
| Concept learning | Explainer for a missed skill taught as a reusable procedure (Claim → Test → Match), with 2–3 "sibling" questions the student has never seen | ✓ (PSAT cluster pipeline) → ✚ for any bank |
| Review | Spaced-repetition due queue (SM-2) that shows old answers hidden and accepts a genuine new attempt — without corrupting lifetime progress | ✓ |
| Exams | Adaptive full mocks, timed modules, pause/resume, break deadlines, and module-1 → module-2 routing | ✓ single-exam → ✚ any program blueprint |
| Offline | "Prepare this exam offline": cache the app shell and only this sitting's images (~15 MB, not the whole bank), take it, sync on reconnect | ✓ |
| Scores | Scaled estimate with a confidence band; shows "not enough data" below the sample gate; never prints *Official* off an uncalibrated curve | ✓ |
| Habits | Active streak, 7-day study time, domain/skill mastery progress bars, SRS due count | ✓ |
| Cross-subject agenda | One "what should I do next" queue across every exam the student is enrolled in: overdue SRS first, then repeated misses, then unseen coverage | ✚ (today there is one subject) |
| Accommodations | Per-student settings for untimed mode, extended time, allowed calculator/reference, and rest breaks — carried as student config, not code branches | ✚ (untimed focused tests exist; this generalizes it) |
| Transfer check | Prove mastery by solving a new sibling under test conditions, not by improving on a previously seen item | ✚ (partial — explainer pipeline has sibling practice, not a gated mastery state) |
| Notes / flag | Per-question scratch note and "ask adult" flag so a confused item can surface in the parent narrative | ✚ |

**Parent / guardian (and admin) perspective**

| Area | Capability | Carry over? |
| :--- | :--- | :--- |
| Oversight | Empirical score forecast, streak, weekly study time, domain mastery, gap alerts (skill accuracy below threshold), SRS due count | ✓ |
| Drift detection | Per-skill accuracy over time with a "recent decline" alert instead of only a point-in-time snapshot | ✚ |
| Planning | Build a focused test by topic + count + minutes; preview equals what actually launches, shortages are explicit, never silently shrunk | ✓ |
| Assignment | Send a drill or "due this week" plan to a specific child, visible in that child's agenda | ✚ |
| Multi-student | Household switcher, per-child dashboards, side-by-side comparison | ✚ (first-class requirement) |
| Exam administration | Define/edit an exam config (sections, timing, scoring, adaptive rules) and load a question bank against it | ✚ (the core framework feature) |
| AI narrative | Weekly plain-language trend summary + suggested focus areas, with model id / prompt hash / "estimate vs fact" labels attached | ✚ |
| Data & recovery | Export/import with validate → preview → explicit Merge/Replace/Cancel, pre-action snapshots, restore, sync health | ✓ single-student → ✚ per-child, auth-scoped |
| Privacy & consent | Per-household PII scoping, export, and delete-rights; insights can be disabled per child | ✚ |

Two rules govern every feature on both sides, carried from this repo's hard-won culture:

1. **Any number shown is a measurement or is labeled as not one.** Score gates (`MIN_PER_SECTION`), confidence bands, and `measured` vs `assumed` timing apply identically in the child-facing and parent-facing render. A drift alert must not invent a trend from two points with no timestamps.
2. **Any feature that overwrites or deletes is reversible.** Assignments, imports, resets, and sample-data activation snapshot first and name the restore path in the confirm text. A parent override never silently erases a child's attempt log.

## 3. Stack recommendation and rationale

Evaluated against the required properties, not habit.

### Recommendation

**TypeScript (strict) as the single language for core, API, and UI, with a functional discipline and no FP-first runtime. React + Vite for UI. Node test runner / Vitest for core. Playwright for browser. Postgres as source of truth. S3-compatible object storage for assets. Containers (not proprietary serverless). Terraform for infra.**

| Property | Choice | Why |
| :--- | :--- | :--- |
| Strong typing | TypeScript `strict`, no `any`, io-ts/Zod at I/O boundaries | Exam plugins are mostly data shapes. The historical bugs were imagined schemas (`question_type` / `prompt` on 0 of 3,059 records). A typed `Question` decoded once at the bank boundary would have made that a compile/parse failure. Clojure’s specs are good; they are not as agent-native as Zod + TS. |
| Functional style | Pure functions + immutable values **in `packages/core`**, enforced by lint and by “no I/O in core” rather than by a Lisp | The current engine already proves this pattern in JS. Plug-in extension is “new module that implements `ScoreModel` / `GradeFn` / `BlueprintPlanner`”, not “edit `scoring.js`”. |
| FP-first language? | **No.** Not ClojureScript, not Elm, not Haskell-to-JS | See below. |
| Separation of concerns | Monorepo packages with import bans (UI cannot import SQL; core cannot import React or `fs`) | Today’s page controllers import Desmos, Chart.js, sync, and grading-adjacent UI in one file. Package boundaries make that a lint error. |
| Data sanctity | Append-only event log in Postgres, materialized views, no update-in-place of attempts | Directly finishes Milestone 3. Cosmos+merge was a clever CRDT over a document store; it still loses concurrent attempts. |
| Agent-ease | Explicit modules, small pure functions, Zod schemas as the interface, tests next to code, no script-order globals | Agents fail on ambient knowledge (`__PSAT_ENGINE_PARTS` load order, `sed` in deploy scripts, twin copies). They succeed on “implement `GradeFn`, here is the schema and the failing test.” |
| TDD | Vitest for core (ms feedback), Playwright for UI contracts, generative tests for merge/retention | Matches this repo’s already-correct testing religion. A Lisp REPL is lovely for humans; it is not how current coding agents iterate. |
| Deploy loop | Preview deploy per PR (Cloudflare Pages / Fly) + migrate-forward Postgres; promote immutable artifacts | Azure SWA + Functions + hand scripts (`deploy_v2.sh` transforming bytes) is slow and promotes untested artifacts (§3.7 of the ring design). |
| Performance (tie-break) | Static UI on a CDN, lean sittings, no 6 MB bank on first paint | Same performance budget the current app earned the hard way. |

### Why not a functional-first language

This is a genuine judgment call. I lean **against** ClojureScript (and Elm) for this project, not because FP is wrong.

**For CLJS:** immutable defaults, data-oriented plugins (EDN exam configs), Reagent/re-frame as a perfect match for “events in, views out,” and a culture that would have prevented a lot of the mutable progress-map pain.

**Against, and they outweigh for *this* codebase:**

1. **AI coding agents will implement this.** Agent training mass and tool quality are overwhelmingly TypeScript. The existing engine, tests, and Playwright harness are JS. A CLJS rewrite throws away the one thing this repo proved — a Node-importable pure core with real-data tests — and replaces it with a toolchain agents regularly get wrong (macros, advanced compilation, externs).
2. **The hard problems are not syntactic mutability.** They are schema honesty, concurrent devices, deploy isolation, and “don’t show a fake official score.” TypeScript + freeze/lint + event log addresses those. Clojure does not magically produce a better `ScoreModel`.
3. **UI and ops ecosystem.** Playwright, Vite, Zod, Postgres drivers, OIDC libraries, and object-storage SDKs are boring in TS. In CLJS they are interop projects.
4. **A functional *discipline* on TS gets 80% of the plug-in benefit.** Ban classes in `core`, ban mutation of arguments, require `Readonly<>`, inject clocks and RNGs (already the house style in `test_planner.js` / `exam_state.js`). That is what made WI-10 work. A new language is not required to keep doing it.

If a human team fluent in CLJS were the implementers, I would flip this. They are not.

I would also skip heavy TS FP libraries (`fp-ts`, Effect) in core. They add ambient vocabulary agents misuse. Prefer plain functions, tagged unions, and `Result` types you own in ~50 lines.

### UI framework

**React + Vite**, not continued buildless HTML. The zero-build constraint was right for a four-page family app on blob storage. A multi-program, multi-student app will grow routes (student, parent, admin/program editor, sitting runner, insights). React is the agent-default and has the Playwright story. Keep the UI dumb: components render view-models produced by core. Do not put SM-2 or scoring in hooks.

Svelte is a reasonable second; I expect other reports to pick it for less boilerplate. I prefer React only because agent + test ecosystem is the stated priority.

### What I would not pick

- **Stay on Azure Functions + Cosmos.** Measured: 2 MB item limit drove sharding; Y1 has no slots; SDK and IaC are proprietary; anonymous Functions are the security model.
- **Stay buildless vanilla.** It fought testability for six rounds until WI-09 moved inline JS out of HTML. Going back to four HTML monoliths for a framework is repeating root cause 1 in `REFACTOR_PLAN.md`.
- **Mongo / Dynamo / Firestore as the system of record.** Same document-growth trap, weaker constraints.
- **Next.js on Vercel as the core.** Fine for marketing; the sitting runner and offline-first outbox want a static client plus a small API, not a server-rendered app coupled to one host.

## 4. Architecture and module boundaries

Monorepo (pnpm workspaces or Cargo-style packages). Import-lint enforces the arrows; there is no “just this once” from `web` into `postgres`.

```
exam-framework/
  packages/
    schema/          # Zod types: ExamProgram, Item, AttemptEvent, Sitting, Household
    core/            # pure: grade, schedule, planTest, examState, score, gapSummary
    programs/        # plugin packs: psat89/, (later sat/, act/, custom/)
                     # each exports ExamProgram + ScoreModel + item-type extras
    bank/            # content loaders, image/asset index, bank validation
    api/             # HTTP: auth, event ingest, sitting CRUD, bank queries
    web/             # React app: student, parent, admin; theme package inside
    insights/        # InsightProvider interface + adapters + artifact store
    testkit/         # fixtures, real-bank runners, property generators
  infra/             # Terraform: container app, Postgres, object store, CDN
  e2e/               # Playwright against fake API + seeded events
```

### How a new exam is added (the plug-in path)

1. Add `packages/programs/foo/` with `program.ts` (blueprint, timing, honesty gates) and `scoreModel.ts`.
2. Drop a bank through `packages/bank` validation (schema + asset presence + no silent field invention).
3. Register the program id in a manifest. No edits to `core` or `web` unless a *new item type* or *new sitting chrome* is required (calculator, passage pane, audio).
4. Tests in `programs/foo/` run `planTest` / `score` against the real bank and assert counts — the CLAUDE.md prime rule, per program.

If adding AP Calculus requires editing `packages/core/score.ts`, the boundary failed.

### How a new analytics view is added

`core` already emits facts (`gap_summary` shape, Wilson intervals, session ledgers). A view is a React component over a view-model function in `core` or `web/features/`. It must not re-derive counters from the 3-attempt tail; it reads the materialized view. This is the structural fix for “parent required ≥3 attempts, student page didn’t.”

### Layer rules

- **`schema`:** no functions beyond parse/serialize. One source of truth for wire + storage + UI forms.
- **`core`:** no `Date.now`, no `Math.random`, no `fetch`, no DOM. Every export is pure. This is today’s `js/engine/` minus `storage.js`/`sync.js`.
- **`api`:** authenticates, appends events, projects views, signs asset URLs. Idempotent ingest on `attemptId`.
- **`web`:** theme (`tokens` + components) is swappable; the sitting runner is a feature module that can be replaced (e.g. a future native shell) because it talks only to `core` + API client.
- **`insights`:** depends on `schema` + read models, never on `api` internals. Swapping OpenAI for Anthropic for “none” is an adapter file.

### Persistence model (the real architecture)

```
append AttemptEvent / SittingEvent / AdminEvent
        ↓  (never update, never delete; corrections are new events)
  projector (pure, in core, run in API and optionally in the client for offline)
        ↓
  read models: Progress, SrsCard, SessionDay, ExamReport, GapSummary
```

Offline: the client keeps a local event log (IndexedDB, not five `psat_*` keys) and an outbox. Reconnect appends; the server’s uniqueness on `attemptId` makes retries safe. Derived views are rebuilt. This replaces both the Cosmos shard codec and the 3-attempt cap as the source of truth — the cap can remain as a *display* window.

Destructive parent actions (Replace import, reset) emit a `SnapshotTaken` event and a `ResetApplied` event; they do not UPDATE rows to empty. Restore is “project from events before T.”

### What this prevents vs the current “hard refactor per feature”

| Current pain | Structural prevention |
| :--- | :--- |
| Twin pages reimplement gates | One `scoreEstimate(program, facts)` used by every surface |
| Preview ≠ launch | Planner in `core`; UI cannot size a test another way (import ban on `examgen`-style helpers from pages) |
| New exam type edits scoring + gen + UI | Program pack; UI is generic over `ExamProgram` |
| UMD load-order deploys | Bundled `web` with explicit package imports |
| 2 MB document + slim codec | Events in Postgres; no document to overflow |
| `/v2/` writes live student | Authz on household; environments have separate DB names, not URL prefixes |

## 5. Cloud, deployment, and environment rotation (pre/prod/old)

### Primary cloud

**Portable default:** Cloudflare (Pages + R2 + CDN) for the static client and assets; **Fly.io** (or GCP Cloud Run) for the API container; **Neon Postgres** (or Cloud SQL / RDS) for the event log and read models; Terraform everywhere.

I would **not** stay on Azure as the primary, despite the current production estate. The measured reasons are in this repo: Cosmos item limits, Functions Y1 with no slots, proprietary backup semantics, and a blob `$web` root that cannot symlink. Azure is an acceptable *implementation* of the same design (Container Apps + Azure Database for PostgreSQL + Blob) if the operator wants one vendor; it is not the design.

**Exception I would accept:** keep the existing Azure Blob copy of PSAT PNGs as a content origin during migration, because those 3,059 images are copyrighted exam content and already have a known home. Point the new asset layer at them until a proper private bucket with signed URLs exists. Do not keep Cosmos as SoT.

### Rough monthly cost (single-digit households, hundreds of attempts/month)

| Item | Low-usage estimate |
| :--- | :--- |
| Postgres (Neon launch / small Cloud SQL) | $0–19 |
| API container (scale-to-zero Cloud Run, or one shared Fly VM) | $0–12 |
| R2/S3 + CDN (bank images, mostly cache hits) | $1–5 |
| Auth (Clerk free tier, or Lucia + email on the API) | $0 |
| Observability (one small Axiom/Grafana cloud) | $0–15 |
| **Subtotal, no AI** | **~$5–40** |
| LLM insights (explanations + weekly parent narrative) | $5–30 depending on cache hit rate |
| **Plausible household total** | **$15–70** |

This is cheaper and more predictable than Azure Cosmos serverless + Functions at idle-with-spikes, and it does not have a 2 MB cliff. AI is the only term that can dominate; the seam in §6 must cache.

### The pre → prod → old ring

Adopt the pointer model already drafted in `docs/RELEASE_RING_DESIGN.md` §4, but make it infrastructure instead of `$web` prefixes.

```
artifacts/           immutable, content-addressed (OCI image + static tarball)
  sha-abc123/
  sha-def456/

pre  → sha-abc123     (preview URL)
prod → sha-def456     (live URL)
old  → sha-90ab12     (previous prod, still serving)
```

Promotion retargets pointers (CDN/custom-domain rules, Fly app scaling, or a thin nginx/Caddy). **Never rebuild on promote** — this repo already learned that `deploy_v2.sh` mutates files at staging time, so the thing promoted is not the thing tested.

**Data is not in the slots.** App rollback must not roll back student events.

```
                    ┌─────────────┐
  pre  ──API_URL──► │ postgres-pre│   (cloned, anonymized)
                    └─────────────┘
  prod ──API_URL──► │ postgres-prod│  ← the only SoT for live attempts
                    └─────────────┘
  old  ──API_URL──► │ postgres-prod│  same DB, older app
```

Implications:

1. **`old` and `prod` share `postgres-prod`.** A rollback from prod to old does not strand recent attempts: they are rows, not files in the static bundle. Constraint: **app versions must be forward-compatible with the event schema** (ignore unknown event types; never require a column the old app cannot read). Event schema is append-only: new optional fields, new event `type` values, no renames.
2. **If a release includes a breaking projector change,** it deploys a dual-read projector *before* the UI that needs it. Rollback of UI is then safe; rollback of a destructive migration is not — so we do not do destructive migrations.
3. **`pre` never shares prod data.** Clone job: dump prod events, rewrite `householdId`/`studentId`, drop PII (names, emails), load into `postgres-pre`. Copy asset references as-is. Do **not** reassemble shards into a tidy map — that class of bug is documented (`RELEASE_RING_DESIGN.md` §3.5 / §3.6: `cloneProdDataToBeta` only copies four `localStorage` keys and cannot seed pre). Re-clone at the start of each test cycle.
4. **One-way by construction.** Pre credentials cannot write to prod (separate DB, separate secrets, server-side `ENV=pre` that the API enforces — not a path prefix the client claims).
5. **Service worker / caches.** Network-first shell (already the WI-20 policy). Slot change must bump the SW version so `old` users who rolled back are not stuck on a cached `prod` shell. Do not register a root-scoped worker that spans slots.

### Backups and restore

- **Postgres:** point-in-time recovery (Neon PITR / RDS PITR) as the primary, plus nightly `pg_dump` to object storage with checksum sidecars — keep the spirit of `backup.js` (checksum, zero-document/zero-byte guard, dry-run restore default, never overwrite a good archive with empty).
- **Assets:** versioned bucket, separate from DB backups (the current gap: images are in git + `$web` with no immutable backup).
- **Verify:** a weekly restore into a scratch Postgres, run the projector, assert event counts and a known student checksum. A restore that is never applied to scratch has not been tested — also a lesson from this repo.
- **Client:** keep pre-destructive local snapshots and an export file; they are household recovery, not the SoT.

## 6. AI insights integration

AI is a **read-only annotator** of facts the core already believes.

### Seam

```ts
interface InsightProvider {
  id: string;                 // "anthropic:claude-x", "openai:gpt-x", "none"
  explainItem(input: ExplainItemInput): Promise<ExplanationDraft>;
  narrateProgress(input: ParentNarrativeInput): Promise<NarrativeDraft>;
  suggestFocus(input: GapSummary): Promise<FocusSuggestion[]>;
}
```

- Lives in `packages/insights`. Core and API depend only on the interface.
- `none` is a real adapter (returns empty + `available: false`) so a household or a test never talks to a network.
- Provider id + prompt template version + input hash are stored on every artifact. Regeneration is a new row; old artifacts remain for audit (“what did the parent see last Tuesday”).
- The sitting UI may *link* to an explanation; it may not block grading on the model.

### Where it sits

```
AttemptEvent  →  projector  →  GapSummary / SittingReport
                                      ↓
                              insights.explain / narrate
                                      ↓
                              InsightArtifact (object store + DB row)
                                      ↓
                              web: parent narrative, item explainer pane
```

The current cluster-explainer pipeline (`explanations/SYSTEM.md`: misses → worklist → mental model → HTML page → `index.json`) becomes a **content pack** that a provider can retrieve first. Human-authored cluster pages stay the gold standard for PSAT 8/9; the model fills gaps and writes parent prose. Do not let the model overwrite the question card or the answer key.

### Safety, inherited from this repo

- Models do not invent scores. Narratives consume `ScoreEstimate` (which may be `null` + `reliable: false`).
- Models do not invent the student’s choice. Only cite `selectedAnswer` if the event has it (EXPLAINER_BRIEF rule 4).
- PNG/card bytes are the authority for any number cited in an explanation when `text_complete` is false — the provider is given the image, not just JSON text.
- Generated HTML/Markdown is sanitized; no provider HTML is executed as a page controller.

## 7. Trade-offs and where other models may disagree

These are the decisions I would expect a meta-report to actually argue about.

1. **TypeScript-with-discipline vs ClojureScript/Elm.** I chose TS because agents will write the code and because this repo already has a pure JS core worth stealing as a pattern. A more FP-orthodox report will call that a lack of nerve and pick CLJS or even F# / Reason. The disagreement is about *who implements*, not about whether core should be pure.
2. **Event sourcing vs “just use Postgres rows.”** I want an append-only attempt log because DATA-01 is still open and because reset/import/rollback are product features. Other reports may call full event sourcing overkill for a household app and propose a mutable `attempts` table with unique `(studentId, attemptId)` and `ON CONFLICT DO NOTHING`. I would accept that as a * paler* version of the same idea; I would not accept last-write-wins documents.
3. **Leave Azure vs stay and wrap.** Operators who already have Cosmos, a blob site, and working nightly backups may prefer “Postgres later, auth now, stay on Azure.” I think Cosmos taught the wrong data model (shards, slim codecs, 2 MB) and Y1 cannot do the ring. Staying is cheaper this quarter and more expensive the first time a second student or a second exam appears.
4. **React vs Svelte vs stay vanilla.** React is the agent-default. Svelte is less ceremony and closer to the current DOM style. Vanilla + Web Components would preserve the no-framework ethic in `REFACTOR_PLAN.md` §2.2. I dropped vanilla because the page controllers are already 3,000-line evidence that “no framework” does not equal “separated UI.”
5. **How much of the current engine to copy.** I would port the *algorithms and tests* of `grading.js`, `scheduler.js`, `exam_state.js`, `test_planner.js`, `merge` monotonicity, and the honesty gates — not the UMD loader, not `psat_*` keys, not Cosmos sharding. Other reports may propose wrapping `PSAT_ENGINE` as a plugin behind a facade to save time. That saves a month and donates the identity/config coupling to the new system.
6. **Auth weight.** I assume real accounts (email magic link + passkeys, household invites). A dissenting report may keep “family PIN on a shared device” because the current user is one student. That fails the “multi-student from day one” requirement as soon as two kids share a tablet, but it is simpler and closer to today’s threat model (anonymous API on a secret URL).

## 8. Open questions for the human reviewer

1. **Who is the customer in year one?** One household with several kids and several exams, or many unrelated families / a tutor with a roster? Auth, tenancy, and cost look different (Neon vs something that needs row-level isolation reviews).
2. **Are College Board (and other) item images still served from a family-controlled origin?** A generic framework that hosts copyrighted banks needs a legal and access model the current private blob site has been able to dodge.
3. **Must offline full-sittings remain a hard requirement?** WI-20’s airplane mode drives SW scope, asset packaging, and “local event log.” If the answer is yes, IndexedDB + outbox is non-negotiable and a server-rendered app is the wrong shape.
4. **Is “parent” the only adult role, or is there a teacher/class?** The current parent portal mixes oversight, exam builder, and backup admin. A teacher of 30 needs rostering the household model does not provide.
5. **Score calibration:** keep shipping labelled estimates (current honesty) or invest in psychometric calibration per program? The framework should support both; the PSAT pack still has unvalidated curves.
6. **Migration of the live `default_student` history.** Event-source from day one for new programs is easy. Replaying 800+ answers, 24 sittings, and SRS cards into events without changing a number the parent already saw is a one-time project that needs a freeze window and a parallel-run against the current merge semantics.
7. **Agent implementation constraint:** is the next builder still “AI sub-agents, one work item each” (`REFACTOR_PLAN.md`)? If yes, the package boundaries and “failing test first” rules should be written as the new CLAUDE.md *before* any feature work.
8. **Environment ring vs preview-per-PR.** The three-slot ring matches this family’s operational reality (one live student, human-approved promote). A multi-tenant SaaS would instead do ephemeral PR previews + prod + PITR. Which operating model are we actually designing for?

Until (1), (3), and (6) are answered, I would build the kernel (schema, core, event ingest, one PSAT program pack, one household, Playwright) and refuse to port the Cosmos document shape forward.
