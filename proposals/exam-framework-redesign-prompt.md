# Generic Exam Prep Framework — Redesign Proposal Prompt

## Objective

**You are not implementing anything.** Your job is to analyze the existing project (code, architecture, data model, and the product learnings baked into it) and produce a **written proposal report** on how you would design a generic, multi-subject, multi-student version of it differently — if you were starting fresh with today's best available tools and patterns.

This report is one of several independent reports being generated by different LLMs/agents against the same source project and the same prompt. They will later be compared and merged into a single meta-report by a human. This means:

- **Write your report to a new file in its own output folder** — do not modify the existing codebase, do not open a PR, do not scaffold a new repo. The deliverable is the document itself.
  - **Location**: a top-level `proposals/` directory at the root of the current repo (create it if it doesn't exist), sitting alongside the existing project — not inside `src/` or any app code folder.
  - **Filename**: `proposals/<model-name>-<yyyy-mm-dd>.md`, where `<model-name>` is your own model/agent identifier in lowercase, hyphen-separated (e.g., `proposals/claude-opus-5-2026-09-11.md`, `proposals/gpt-5-2026-09-11.md`, `proposals/gemini-3-pro-2026-09-11.md`). If you're run more than once on the same day, append a numeric suffix (`-2`, `-3`, ...) rather than overwriting a prior report.
  - Do not put your model name inside the document body as a title — the filename is the identifier; the document's first line should still be the `# Proposal: Generic Exam Prep Framework` header from §7.
- **Follow the report structure in §7 exactly**, using the same section headers as specified. Consistent structure across all reports is what makes the later merge possible — don't reorganize or rename sections even if you'd naturally structure your argument differently.
- Where you're uncertain or see a genuine judgment call rather than a clear best answer, say so explicitly and give your reasoning for the direction you lean — the human merging reports needs to see where models actually disagree, not just a confident-sounding answer.

## Context: the project being analyzed

The source project is a single-subject PSAT 8/9 exam prep app: a static, dependency-free frontend (four hand-written HTML pages, vanilla JavaScript, no framework and no build step — engine logic in UMD modules under `js/engine/`, page controllers as native ES modules, state held in `localStorage` and synced to the cloud), an Azure Functions API on a Consumption plan, and Cosmos DB for questions/attempts. A single hardcoded student (`default_student`, derived from the URL path) with no authentication on any endpoint; parent/student dashboards, spaced repetition, adaptive full-mock exams, mistake tracking, and score projection. It worked, but it's single-subject, single-student, and its UX styling and business logic are entangled throughout the codebase.

Start by actually reviewing the code and data model in this repo — don't reason about it abstractly. Your proposal should cite specific things you found (patterns that worked, patterns that will fight against generalization, coupling that would block reuse) as evidence for your recommendations, not generic best-practices boilerplate.

## What the proposal needs to cover

### 1. What this becomes: a generic framework

The redesign target is a framework, not an app: an admin/parent defines an "exam config" (sections, timing, scoring, adaptive rules) and loads a question bank against it; the same engine then handles test-taking, scoring, analysis, explanations, parent oversight, and AI insights — for any subject and any number of students. Multi-student and multi-account support is a first-class requirement from day one, not bolted on later.

Explain in your proposal what in the current design would have to change to support this, and what (if anything) already generalizes cleanly.

### 2. Design principles to evaluate the stack against

Rather than picking a stack out of habit, evaluate candidates explicitly against these properties, and say which stack/pattern combination best satisfies them and why:

- **Strong typing** as a first-class safety net for a codebase that will keep growing across many exam types.
- **Functional programming style** — pure functions, immutable data, minimal shared mutable state — specifically because it's the pattern that best supports *plug-in style extension* (adding a new exam type, scoring rule, or analytics view as a new module) instead of touching-and-retesting existing modules every time something is added. Discuss whether a functional-first language/runtime (e.g., ClojureScript, or a functional-style discipline layered on top of TypeScript, or another option you think is currently state-of-the-art) is worth it here, or whether it adds more friction than it removes — this is genuinely open, give your real assessment.
- **Separation of concerns**, especially UX/styling vs. business logic vs. persistence — each should be independently replaceable.
- **Data sanctity**: student attempt data and history should be effectively append-only / hard to corrupt or silently overwrite, with a clear source of truth. Discuss whether an event-sourced or append-only data model is a good fit here versus a conventional mutable-record model.
- **Ease of programming for AI coding agents specifically** — since implementation will be done by AI agents, not humans, favor patterns that are easy for an agent to work within correctly (explicit interfaces, small pure functions, minimal implicit context) over patterns that are elegant but require a lot of ambient project knowledge to use correctly.
- **Test-driven development** as the default workflow, and what that implies for stack choice (how easy is it to unit-test the core logic in isolation, how easy is it to get strong automated UI test coverage).
- **Fast deployment feedback loops** — how quickly can a change go from written to deployed-and-verified, and what in the stack/infra choice helps or hurts that.
- **Speed/performance** of the resulting app for end users, as a tie-breaker where other properties are close.

### 3. Architecture

Propose a concrete module/repo structure that enforces the separation above (core logic, content/schema, API, UI + theme layer, AI insights, infra), and explain specifically how the structure prevents the "hard refactor for every new feature" problem versus enabling "add a plug-in module."

### 4. Cloud & deployment

Recommend a primary cloud provider and stack, but favor portable/standard components (Postgres over proprietary NoSQL, standard containers over proprietary serverless formats, Terraform over provider-locked IaC) unless there's a strong reason not to — flag any such exception. Estimate rough monthly cost at low usage (single-digit households, hundreds of test attempts/month).

Address the three-environment rotation model: **pre** (QA) → **prod** (live) → **old** (previous prod, rollback target), where promoting `pre` to `prod` retires the current `prod` to `old`. Explain how student data stays intact and reconcilable across that rotation (so a rollback from `prod` to `old` doesn't strand recent attempts), how `pre` gets safe non-production data to test against, and how backups/restore are handled and verified.

### 5. AI insights

Propose the interface/seam for AI-generated content (explanations, parent-facing trend narratives, suggested focus areas) so the underlying model/provider is swappable, and note where in the architecture this seam lives.

### 6. Trade-offs and disagreement points

Explicitly list the 3-5 decisions where you expect other models/agents doing this same analysis might land differently than you did, and why. This section is what makes the meta-report merge valuable — don't skip it or hedge it into nothing.
